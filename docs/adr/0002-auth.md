# ADR-0002: Autenticación con JWT propio (sin Azure AD B2C)

**Estado:** Reemplazada por [ADR-0005](0005-migracion-azure-a-aws.md) — el mismo razonamiento aplica ahora frente a AWS Cognito. Se conserva como registro histórico.

## Contexto
El MVP de Refugia está acotado a un solo refugio (sin multi-tenant), con dos perfiles de acceso: staff del refugio (login) y público (solo lectura de animales disponibles, sin login).

## Alternativas consideradas
| Alternativa | Ventajas | Trade-offs |
|---|---|---|
| JWT emitido por la propia API | Simple de implementar y explicar, proporcional a la complejidad real (un solo rol autenticado) | Hay que manejar rotación de secretos y expiración a mano |
| Azure AD B2C | Robusto para escenarios multi-tenant, MFA, social login | Sobredimensionado para un solo refugio y dos roles; agrega complejidad de configuración sin necesidad real en el MVP |

## Decisión
JWT propio, emitido por la API tras login del staff. Sin login para el público (endpoints de solo lectura abiertos).

## Justificación
Con un solo refugio confirmado como alcance del MVP, no hay necesidad de gestión de identidad multi-organización. Introducir Azure AD B2C ahora sería complejidad no justificada por el problema — contradice el criterio de "la tecnología se deriva del problema" que guía este proyecto.

## Consecuencias
- Impacto en negocio: ninguno, mientras el alcance sea un solo refugio
- Impacto técnico: capa de auth simple (middleware de verificación de JWT), sin dependencia externa de identidad
- Riesgos asumidos: si el proyecto evoluciona a multi-refugio, esta decisión debe revisarse
- Extensión futura: migrar a Azure AD B2C (o similar) el día que se necesite soportar múltiples organizaciones con aislamiento de datos entre ellas — documentar como ADR nuevo que reemplaza este, no como parche
